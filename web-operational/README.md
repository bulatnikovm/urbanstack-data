# Операційний дашборд UrbanStack

Next.js 16 + shadcn/ui + Bklit UI поверх `dbt_operational`. Окремий застосунок
від продуктового (`../web`) — окремий деплой, окремий домен, окремий реєстр
метрик.

Дві сторінки: **Огляд ЖК** і **Ризик відтоку**. Далі сюди переїжджають заявки,
SLA і опитування з Looker.

## Як влаштовано

Так само, як у продуктовому: дані вивантажуються з BigQuery в закомічений JSON,
сторінка рендериться з нього, глядачі не навантажують BigQuery.

```
dbt build
  → npm run export-data    BigQuery → data/*.json  (16 файлів, ~3,4 MB)
  → npm run build-metrics  docs/metrics_operational.yml → data/metrics.json
  → git commit + push      Vercel бачить пуш і перезбирає
```

Автооновлення — той самий воркфлоу, що й у продуктового
([`.github/workflows/refresh-dashboard.yml`](../.github/workflows/refresh-dashboard.yml),
06:00 UTC): один `dbt build` на обидва домени, далі два окремі `npm ci` +
`export-data` (залежності й lock-файли в застосунків свої), і один коміт на
обидві теки `data/`. Vercel бачить пуш і перезбирає обидва проєкти.

⚠️ **Деплой вимагає ОКРЕМОГО Vercel-проєкту** на тому самому репозиторії, з
Root Directory = `web-operational`. Змінні середовища — свої
(див. `.env.local.example`), окрім списку доступів: він спільний з
продуктовим (та сама таблиця Supabase `dashboard_users`), тому редагується
на `/admin` продуктового дашборду — тут такої сторінки немає навмисно.

⚠️ **`proxy.ts` не перейменовувати.** Він захищає всі сторінки до рендеру;
у гілці розробки лежав як `proxy.ts.OFF-for-local-view`, щоб дивитись
локально без логіна. У такому вигляді на Vercel дашборд відкритий усьому
інтернету. У виводі `next build` має бути рядок `ƒ Proxy (Middleware)` —
це і є перевірка.

## Команди

```bash
npm run dev            # локально
npm run export-data    # перезалити data/*.json з BigQuery
npm run refresh        # export + build
```

Автентифікація експорту — та сама ADC, що й у dbt (`gcloud auth application-default login`).

### CSAT: чотири речі, які легко зламати

- **Середню НІКОЛИ не усереднювати.** Марти віддають `grade_sum` і `votes`,
  а не готовий `avg_grade`, саме тому: середня з будинкових середніх дає ЖК
  неправильний бал (будинок із двома голосами важить як будинок із
  двомастами). Рахувати завжди `SUM(grade_sum)/SUM(votes)` — для цього є
  `csatAvg()` у `lib/data.ts`.
- **Категорію проблем не можна отримати сумуванням її тем.** Коментар
  «брудно в холі й газон не косять» дає +1 «Прибиранню» і +1 «Території»,
  але в категорії «Чистота та благоустрій» він ОДИН. Тому
  `agg_csat_problems` віддає два рівні окремими рядками (`level`), а
  сторінка бере потрібний. Перша версія складала теми й показувала 650
  замість 489.
- **`wave_sort_id` — не ключ хвилі, попри назву.** Це `min(survey_id)` на
  РЯДОК (хвиля × ЖК × будинок), і в межах однієї хвилі він різний для різних
  будинків. `mart_survey_complex_integral` спершу зводить його до справжнього
  ключа (`min` по `wave_label`); наївне `max(wave_sort_id)` дало 1 рядок
  замість 10. Для сортування хвиль у застосунку є `csatWaveOrder()`, який
  іде за `wave_month_key`.
- **Вибірка міряється до КВАРТИР, не до користувачів** (правка Артема).
  Знаменник не залежить від того, скільки людей поставили застосунок, тому
  тільки його можна порівнювати між ЖК. На рівні будинку — квартири САМЕ
  цього будинку. Частка від підтверджених лишається поруч, але відповідає
  на інше питання.
- **Графік «Оцінка по хвилях» ходить по СПРАВЖНІХ ключах місяця.** `LineChart`
  тут часовий — він парсить вісь як дату, і текст мітки хвилі
  («Охорона трав. 2026») ламав її в нечитабельне «січ. 25 р. — січ. 26».
  Місяці без хвилі лишаються `null`, а не 0: `tooltipRows` тепер такі ряди
  пропускає, інакше тултип писав «Прибудинкова 0» там, де опитування просто
  не проводили.
- **Дейт-пікера на цій сторінці немає — навмисно.** Опитування живуть
  ХВИЛЯМИ (7 хвиль за 9 місяців, у деяких місяцях дві, у деяких жодної), і
  місячний діапазон обіцяв би вибір, якого в даних немає. `PageHeader`
  показує пікер, тільки якщо передані `range` і `bounds`.

### Заявки: три пастки, на які легко наступити

- **«Виконано» може бути більше за «Створено» в тому самому місяці.** Це не
  помилка: створення датується `created_at`, закриття — `closed_at`, тож у
  місяць, коли розбирали накопичену чергу, закритих більше за поданих. Для
  питання «скільки встигаємо по гарячому» є окремий показник
  `sla_rate_same_month`, який за побудовою не перевищує 100%. У `note` панелі
  це написано — не прибирати.
- **Дві різні бази заявок на сусідніх сторінках, і обидві правильні.**
  `/sla` рахує ВСІ подані (`created_count`) — це вхідний потік.
  `/requests` і `/load` рахують лише ДІЙСНІ (`valid_created_count`,
  `valid_count`) — це робота, що реально прийшла. Перша версія `/requests`
  змішала їх, і на одній сторінці стояли 851 і 786 як та сама «Проблема».
  Марти тримають обидва поля поруч саме тому.
- **Навантаження й індекс проблемності показуються × 100.** На одне
  приміщення навантаження це 0,029, а індекс — 0,2 / 0,1 / 0 на всьому
  топ-15; рейтинг переставав бути рейтингом. У даних поля лишаються часткою,
  множення живе тільки в UI.

### Дві метрики, які лишились на дашборді, але нічого не міряють

Обидві перенесені зі старого звіту Looker заради наступності, обидві
позначені `known_issue` в реєстрі — читати їх як показник не можна:

- **Тип «Скарга»** практично не проставляється: 990 заявок зі 164 201 за всю
  історію (0,6%), в окремих ЖК за пів року 0-8 штук. Весь старий
  «Антирейтинг скарг» стояв на цьому полі. Справжнє невдоволення сидить у
  ТЕКСТІ звичайних заявок — його ловлять `/churn` і `/segments`.
- **«Задач на проблему»** — константа: 1,01 / 0,98 / 0,96 / 0,99 / 1,01 по
  роках 2022-2026. CRM заводить рівно одну задачу на заявку, тож відношення
  приречене бути одиницею. З картки прибрано, лишилось приміткою.

### Три осі, які не можна складати

Обидві сторінки показують ту саму систему з різних боків, і головне правило —
осі ризику **не зводяться в одне число**:

* **сходинка конфлікту** (0-5) — що відбувається: роздратування → юридизація
  → організація → намір → пішли;
* **склад населення** — хто живе: частка напружених мешканців, поріг —
  перцентиль усередині портфеля;
* **згасання** — чи з нами ще розмовляють.

Будинок буває тихим і вже втраченим («Севен»: за 12 місяців до виходу жодного
мешканця вище «Спокійного») або гучним і стабільним («Грейт»). Одна шкала ці
випадки схлопує, тому в таблиці три колонки, а не один бал.

⚠️ **Гістерезис у черзі.** Черга сортується за `max(risk_stage,
risk_stage_max_6m)`, а не за поточною сходинкою. Причина не теоретична:
будинок 10 «Варшавський Плюс» за МІСЯЦЬ до виходу випадав зі списку, бо
кампанія вийшла за тримісячне вікно і сходинка впала з 3 на 1.

⚠️ **Персональних списків тут немає і не буде.** Сегмент людини — це
профілювання за персональними даними; поіменний список іде керівнику
комунікацій, на дашборд — тільки агрегати.

## Два різних періоди — і чому їх не можна плутати

`lib/data.ts` має ДВІ функції періоду з протилежною поведінкою щодо
поточного місяця, і це навмисно, не недогляд:

- **`getOverviewPeriod()`** (Огляд ЖК) ПОКАЗУЄ поточний незавершений місяць
  (`isPartial`, позначка «місяць триває»), як і в продуктовому дашборді.
  `mart_monthly_complex_overview` — знімок «скільки нас станом на зараз» для
  кожного календарного місяця, тримісячних ковзних вікон там немає, тож
  неповний місяць просто означає «дані станом на сьогодні», без спотворень.
- **`getChurnPeriod()`** (Ризик відтоку) поточний місяць НЕ показує.
  `mart_house_churn_risk_monthly` рахує тримісячні ковзні вікна, які на
  неповному місяці просідають штучно, і стадія «пішли» спрацьовує на
  половині будинків.

`getSlaPeriod()` / `getRequestsPeriod()` / `getLoadPeriod()` — з першого типу
(поточний місяць показуємо), бо марти заявок теж помісячні знімки подій, а не
ковзні вікна. Усі три побудовані на спільній `buildPeriod()`, щоб цей блок не
розповзся в пʼяту копію.

⚠️ Межі дейт-пікера на `/requests` беруться з `agg_load_monthly` (повна
історія), а НЕ з категорій: категорії вивантажуються вікном 24 місяці, і якби
межі йшли звідти, з дашборду мовчки зникла б уся історія до 2024-го.

Додаючи нову сторінку — спершу зʼясувати, до якого типу март ближче, а не
копіювати одну з двох функцій за замовчуванням.
- **Ряд стрибкий — це не баг.** Одна кампанія на весь ЖК піднімає всі його
  будинки одночасно: у липні 2026 одне звернення про протипожежну систему
  перевело 11 будинків у «організацію» за два дні (15 → 37 у зоні уваги).
  У `note` панелі це написано — прибирати не можна, інакше читається як збій.
- **Два найбільші вивантаження пишуться СЛОВНИКОВИМ форматом.** Значення
  повторюваних колонок (UUID будинку, назва категорії) замінені на індекс у
  словнику, рядок став масивом чисел; читає це `loadCompact()` у
  `lib/data.ts`, сторінки різниці не бачать. Наївний JSON давав 6,1 МБ на
  `agg_orders_house_monthly` — а цей файл перезаписується щодня, і платить за
  розмір історія git, не браузер. Після кодування 0,5 МБ, разом по `data/` —
  2,7 МБ замість 10 МБ.
- **`agg_churn_houses` обрізаний тричі** (12 місяців, лише потрібні колонки,
  лише будинки що бодай раз були в зоні уваги): 791 рядок / 342 KB замість
  5 156 / ~1 MB. Оновлення даних тут = коміт, тож повна марта означала б
  сотні мегабайт історії на рік заради даних, яких сторінка не показує.
- **Стадії 0–5 — це пріоритизатор, а не модель.** Подій виходу за три роки 13;
  пороги підібрані по перцентилях і задокументовані в самій dbt-моделі.
  Перевірка на історії: прапорець піднявся в 11 із 13 будинків, що реально
  пішли. Не називати це «передбаченням» ні на сторінці, ні в презентації.
- **CSAT сюди не входить.** 3 750 із 3 794 відповідей опитувань не мають
  `house_id` — голосування створюється одне на весь ЖК. Єдине джерело оцінок
  з привʼязкою до будинку — оцінки закриття заявок (`order_reviews`).
- **Адмінки доступів тут немає.** Вона лишається в продуктовому дашборді: два
  редактори одного allowlist — це два джерела правди. Пункт меню лишився в
  коді `app-sidebar.tsx` за прапорцем, щоб не вигадувати його заново.

## ⚠️ Дублювання коду з `../web`

`components/`, `lib/format.ts`, `lib/period.ts`, `lib/xlsx.ts`, `auth.*`,
`proxy.ts` — це КОПІЯ продуктового застосунку. Так вирішено свідомо (окремий
дашборд = окремий деплой), але наслідок теж реальний: Bklit UI
(`components/charts/`, ~90 файлів) тепер існує у двох екземплярах і
розʼїдеться при першій же правці в одному з них.

Коли це почне заважати — виносити спільне в workspace-пакет
(`packages/ui`, `packages/lib`) і підключати обидва застосунки як workspaces.
Робити це ЗАРАЗ сенсу мало: поки сторінка одна, рефакторинг робочого
продуктового дашборду коштує дорожче за дублювання.

Що НЕ копіювалось: сторінки продукту, `components/health-filters.tsx`,
`components/trend-charts.tsx`, адмінка.

## Авторизація

Та сама схема, що й у продуктовому: Auth.js v5, Google-логін, allowlist —
у Supabase (`dashboard_users`), не в env (див. `lib/access.ts` і розділ
«Авторизація» в `../web/README.md` — там усі деталі схеми, тут лише
відмінності).

⚠️ `.env.local.example` тут вказує на **той самий** `SUPABASE_URL`, що й у
продуктовому. Якщо це навмисно (обидва дашборди — одна команда, спільний
allowlist), то додавати людину в `/admin` продуктового дашборду досить —
доступ до операційного зʼявиться сам. Якщо `dashboard_users` мають
розійтися (напр. операційний бачить лише частина команди) — заводити
окремий Supabase-проєкт і оновити `SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY`
тут. **Це рішення ще не прийняте явно** — зараз просто працює спільна база,
бо приклад скопійований як є.

`AUTH_SECRET` і Google OAuth redirect — завжди окремі per застосунок
(сесії Next-Auth не повʼязані з тим, спільна база доступів чи ні):
`https://<домен-operational>/api/auth/callback/google`.
