# Операційний дашборд UrbanStack

Next.js 16 + shadcn/ui + Bklit UI поверх `dbt_operational`. Окремий застосунок
від продуктового (`../web`) — окремий деплой, окремий домен, окремий реєстр
метрик.

Дві сторінки: **Огляд ЖК** і **Ризик відтоку**. Далі сюди переїжджають заявки,
SLA і опитування з Looker.

## Як влаштовано

Так само, як у продуктовому: дані вивантажуються з BigQuery в закомічений JSON,
сторінка рендериться з нього, глядачі не навантажують BigQuery.

```
dbt build
  → npm run export-data    BigQuery → data/*.json  (4 файли, ~750 KB)
  → npm run build-metrics  docs/metrics_operational.yml → data/metrics.json
  → git commit + push      Vercel бачить пуш і перезбирає
```

⚠️ **Автооновлення ще НЕ налаштоване.** `.github/workflows/refresh-dashboard.yml`
оновлює тільки `web/`. Для цього застосунку потрібні:
1. окремий Vercel-проєкт з Root Directory = `web-operational`;
2. крок у тому самому воркфлоу (або окремий) з `--prefix web-operational`.

## Команди

```bash
npm run dev            # локально
npm run export-data    # перезалити data/*.json з BigQuery
npm run refresh        # export + build
```

Автентифікація експорту — та сама ADC, що й у dbt (`gcloud auth application-default login`).

## Сторінки

| Маршрут | Сторінка | Про що | Джерела |
|---|---|---|---|
| `/` | Огляд ЖК | скільки будинків/квартир/користувачів по компанії і в розрізі ЖК | `mart_monthly_complex_overview` |
| `/churn` | Ризик відтоку | які будинки рухаються до виходу з-під управління, черга роботи, реєстр кампаній мешканців | `mart_house_churn_risk_monthly`, `mart_campaigns` |

## Два різних періоди — і чому їх не можна плутати

`lib/data.ts` має ДВІ функції періоду з протилежною поведінкою щодо
поточного місяця, і це навмисно, не недогляд:

- **`getOverviewPeriod()`** (Огляд ЖК) ПОКАЗУЄ поточний незавершений місяць
  (`isPartial`, позначка «місяць триває»), як і в продуктовому дашборді.
  `mart_monthly_complex_overview` — знімок «скільки нас станом на зараз» для
  кожного календарного місяця, тримісячних ковзних вікон там немає, тож
  неповний місяць просто означає «дані станом на сьогодні», без спотворень.
- **`getChurnPeriod()`** (Ризик відтоку) поточний місяць НЕ показує.
  `mart_house_churn_risk_monthly` рахує тримісячні ковзні вікна, які на
  неповному місяці просідають штучно, і стадія «пішли» спрацьовує на
  половині будинків.

Додаючи нову сторінку — спершу зʼясувати, до якого типу март ближче, а не
копіювати одну з двох функцій за замовчуванням.
- **Ряд стрибкий — це не баг.** Одна кампанія на весь ЖК піднімає всі його
  будинки одночасно: у липні 2026 одне звернення про протипожежну систему
  перевело 11 будинків у «організацію» за два дні (15 → 37 у зоні уваги).
  У `note` панелі це написано — прибирати не можна, інакше читається як збій.
- **`agg_churn_houses` обрізаний тричі** (12 місяців, лише потрібні колонки,
  лише будинки що бодай раз були в зоні уваги): 791 рядок / 342 KB замість
  5 156 / ~1 MB. Оновлення даних тут = коміт, тож повна марта означала б
  сотні мегабайт історії на рік заради даних, яких сторінка не показує.
- **Стадії 0–5 — це пріоритизатор, а не модель.** Подій виходу за три роки 13;
  пороги підібрані по перцентилях і задокументовані в самій dbt-моделі.
  Перевірка на історії: прапорець піднявся в 11 із 13 будинків, що реально
  пішли. Не називати це «передбаченням» ні на сторінці, ні в презентації.
- **CSAT сюди не входить.** 3 750 із 3 794 відповідей опитувань не мають
  `house_id` — голосування створюється одне на весь ЖК. Єдине джерело оцінок
  з привʼязкою до будинку — оцінки закриття заявок (`order_reviews`).
- **Адмінки доступів тут немає.** Вона лишається в продуктовому дашборді: два
  редактори одного allowlist — це два джерела правди. Пункт меню лишився в
  коді `app-sidebar.tsx` за прапорцем, щоб не вигадувати його заново.

## ⚠️ Дублювання коду з `../web`

`components/`, `lib/format.ts`, `lib/period.ts`, `lib/xlsx.ts`, `auth.*`,
`proxy.ts` — це КОПІЯ продуктового застосунку. Так вирішено свідомо (окремий
дашборд = окремий деплой), але наслідок теж реальний: Bklit UI
(`components/charts/`, ~90 файлів) тепер існує у двох екземплярах і
розʼїдеться при першій же правці в одному з них.

Коли це почне заважати — виносити спільне в workspace-пакет
(`packages/ui`, `packages/lib`) і підключати обидва застосунки як workspaces.
Робити це ЗАРАЗ сенсу мало: поки сторінка одна, рефакторинг робочого
продуктового дашборду коштує дорожче за дублювання.

Що НЕ копіювалось: сторінки продукту, `components/health-filters.tsx`,
`components/trend-charts.tsx`, адмінка.

## Авторизація

Та сама схема, що й у продуктовому: Auth.js v5, Google-логін, allowlist —
у Supabase (`dashboard_users`), не в env (див. `lib/access.ts` і розділ
«Авторизація» в `../web/README.md` — там усі деталі схеми, тут лише
відмінності).

⚠️ `.env.local.example` тут вказує на **той самий** `SUPABASE_URL`, що й у
продуктовому. Якщо це навмисно (обидва дашборди — одна команда, спільний
allowlist), то додавати людину в `/admin` продуктового дашборду досить —
доступ до операційного зʼявиться сам. Якщо `dashboard_users` мають
розійтися (напр. операційний бачить лише частина команди) — заводити
окремий Supabase-проєкт і оновити `SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY`
тут. **Це рішення ще не прийняте явно** — зараз просто працює спільна база,
бо приклад скопійований як є.

`AUTH_SECRET` і Google OAuth redirect — завжди окремі per застосунок
(сесії Next-Auth не повʼязані з тим, спільна база доступів чи ні):
`https://<домен-operational>/api/auth/callback/google`.
