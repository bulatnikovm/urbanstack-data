## 1. Розміри mart'ів — і чому висновок різний по доменах

> **Виправлено v0.2 (Микита).** У v0.1 цей розділ був заміряний тільки по `dbt_finance` /
> `dbt_operational` (продуктових моделей не було видно з гілки плану), побачені гігабайти
> у фінансах, і висновок «потрібен `srv_*`» поширений на всі домени. Для двох із трьох
> доменів посилка не виконується. Нижче — по доменах.

**`dbt_finance` — віддавати назовні не можна ні за яких обставин:**

| Таблиця | Рядків | Розмір |
|---|---|---|
| `mart_billing_flat` | 4 376 518 | 1.83 GB |
| `fct_billing` | 4 557 652 | 1.14 GB |
| `mart_payment_rates` | 3 847 077 | 1.02 GB |
| `mart_debt_flat` | 2 252 013 | 0.98 GB |
| `fct_billing_monthly` | 951 210 | 194 MB |

Це аналітичний grain (приміщення × послуга × місяць). Тут `srv_*` повністю виправданий: агрегація до дашбордного grain'у (ЖК × місяць × бакет) дає тисячі рядків замість мільйонів.

**`dbt_product` / `dbt_operational` — вже serving-розміру, `srv_*` не потрібен:**

| Таблиця | Рядків | Розмір |
|---|---|---|
| `mart_monthly_categories` (ops) | 18 817 | 1.8 MB |
| `mart_app_health_weekly` | 2 416 | 0.2 MB |
| `mart_status_donut` (ops) | 1 155 | 0.1 MB |
| `mart_monthly_complex_overview` (ops) | 816 | 0.2 MB |
| `mart_monthly_sla` (ops) | 590 | ~0 |
| `mart_module_usage_monthly` | 304 | ~0 |
| `mart_star_monthly` | 130 | ~0 |
| `mart_house_rating` (ops) | 106 | ~0 |
| `mart_user_base_totals_monthly` | 32 | ~0 |

**Усі відображувані mart'и обох доменів разом — менше 5 MB.** `srv_` поверх них був би копією один-в-один: той самий grain, ті самі колонки, той самий обсяг. Жодна з трьох причин заводити serving-шар тут не спрацьовує:

| Причина завести `srv_*` | Фінанси | Product / Operational |
|---|---|---|
| Розмір (не влазить у Postgres / дорогий скан) | ✅ гігабайти | ❌ < 5 MB разом |
| Латентність і вартість | ✅ | ❌ і так миттєво |
| Контракт (рефакторити mart, не ламаючи API) | ✅ | ⚠️ досягається дешевше — див. §1.1 |

І головне: копія 1:1, яку треба синхронно правити при кожній зміні mart'у — це **рівно той механізм розходження**, який ми викорчовували з хардкод-списків будинків (`CLAUDE.md` баг #1). Заводити його добровільно, ще й без виграшу в розмірі, — помилка.

Єдиний великий обʼєкт у продукті — `fct_user_monthly` (128 тис. рядків, 36 MB), але це факт, а не те, що показується напряму.

### 1.1 Куди дівається потреба в контракті

Потреба зафіксувати «що саме їде назовні» нікуди не зникає — вона просто не варта окремого шару моделей. Закриваємо дешевше, в трьох місцях:

1. **Export manifest** — один файл зі списком `mart → опублікована таблиця + колонки`, які їдуть у Postgres. Це і є контракт, в одному місці, без дублювання логіки.
2. **dbt `exposures`** — декларуємо дашборд як exposure над конкретними mart'ами. Тоді `dbt build` знає залежність, а той, хто редагує mart, бачить «це живить продуктовий дашборд».
3. **`lib/server/queries/*.ts` + `metrics.yml`** — шар відображення на боці API (§3.1, §3.3). Саме тут перейменування колонки в mart'і гаситься, не доходячи до клієнта.

**Висновок по §1:** `srv_*` агрегати — тільки для фінансів і тільки у Фазі E. Для product/operational експортуємо існуючі mart'и напряму.

## 2. Архітектура

```
  postgresqldim9000 (Stitch-sync з продуктової Postgres)
        │
        ▼
  BigQuery · dbt  (dbt_finance / dbt_operational / dbt_product)
        │  staging → intermediate → marts        ← вже є (Фаза 2)
        │
        ├─ product / operational marts           ← їдуть НАПРЯМУ, вони вже serving-розміру (§1)
        │
        ├─ srv_* агрегати                        ← ТІЛЬКИ для фінансів, Фаза E (§1)
        │
        ├─ srv_metric_timeseries (long format)   ← НОВЕ: зміна ФОРМИ, не копія (§7.1)
        ├─ srv_metric_anomalies                  ← НОВЕ (Фаза D)
        └─ meta_refresh_log                      ← НОВЕ: контракт свіжості (§2.3)
        │
        ▼   export job (після успішного dbt run, атомарний swap)
  Postgres (Supabase, EU) — serving store, десятки тисяч рядків, не гігабайти
        │
        ▼
  API · Next.js route handlers  /api/v1/*        ← auth, ролі, tenant_id, кеш
        │
        ▼
  React · Next.js App Router + shadcn/ui + Bklit UI
```

### 2.1 Чому serving-store, а не читати BigQuery напряму з API

| | BigQuery напряму | Postgres serving store |
|---|---|---|
| Латентність на запит | 1–3 с (холодний старт слотів) | 5–30 мс |
| Сторінка з 12 карток | 12 × BQ job | 1–2 запити |
| 5 людей відкрили одночасно (R4) | 5× сканів, 5× оплати | ≈ 0 додаткової вартості |
| BigQuery лежить / dbt впав (R1) | дашборд лежить | віддається останній валідний зріз |
| Ролі/RLS для white-label (пізніше) | треба городити | вбудовано |
| Вартість | on-demand за скан, на кожен перегляд | фіксована, фактично free tier |

Компроміс, який свідомо приймаємо: **дашборд показує зріз, а не live-дані**. Це нормально — джерело й так Stitch-репліка, тобто live там ніколи не було. Головне — зробити цю затримку **видимою** (R2), а не вдавати, що її немає.

### 2.2 Стабільність — конкретні механізми (R1)

1. **Атомарний swap.** Export пише в `*_staging` таблиці, потім одна транзакція: `BEGIN; DROP old; ALTER staging RENAME; COMMIT;`. Часткових даних глядач не бачить ніколи.
2. **Останній валідний зріз залишається.** Провалився dbt або export — Postgres тримає попередній зріз, дашборд працює, бейдж свіжості стає жовтим/червоним.
3. **Read-only DB user** для API. Дашборд фізично не може нічого записати.
4. **`meta_refresh_log`** — по домену: `last_run_at`, `status`, `rows_written`, `dbt_invocation_id`. Це джерело для бейджа свіжості й для алертів.
5. **API ніколи не ходить у BigQuery синхронно** на рендер сторінки. Виняток — drill-down "показати список боржників" (рідкісний, з окремим кешем і лімітом).

### 2.3 Свіжість — контракт, а не надія (R2)

- Кожна serving-таблиця має `snapshot_at`.
- Кожна відповідь API повертає `meta.snapshot_at` + `meta.freshness` (`fresh` / `stale` / `broken`).
- UI: у шапці "Дані станом на 5 серп 2026, 06:00" + кольоровий стан. Якщо `stale` — банер, а не тихе показування старих цифр.
- **Детектор "дані не доїхали".** Той самий кейс, що вже ловили: липень 2026 у `mart_debt_flat` — 1 рядок замість десятків тисяч (`CLAUDE.md` §8а). dbt-тест: кількість рядків поточного місяця не менша за X% від медіани попередніх 3 місяців. Інакше метрика "борг впав до нуля" піде на дашборд як реальний інсайт — і це найгірший можливий баг у дашборді для СЕО.
- Реальна стеля свіжості = каденція Stitch. Дашборд не може бути свіжішим за неї — треба звірити фактичну каденцію й від неї ставити розклад dbt (див. відкрите питання Q2).

### 2.4 Оркестрація

GitHub Actions cron (репо вже git, окремої інфри не треба):

```
dbt build --select state:modified+  (або повний build — він дешевий на цих обсягах)
  ↓ (тільки якщо exit 0)
dbt test  → фейл = не публікуємо, лишаємо попередній зріз, шлемо алерт
  ↓
export BQ → Postgres (atomic swap)
  ↓
POST /api/v1/internal/revalidate  → скидає кеш Next.js
```

Секрети: GCP service account з read-only на `dbt_*` датасети (окремий від того, що під `gcloud auth` локально) + Postgres connection string. Альтернатива, якщо схочеться все тримати в GCP — Cloud Run Job на Cloud Scheduler; логіка та сама.

## 3. API

### 3.1 Окремий сервіс чи route handlers?

**Рекомендація: route handlers усередині Next.js-репо**, але з дисципліною, яка дозволяє винести.

Чому не окремий FastAPI/Go-сервіс зараз: один деплой замість двох, одна сесія авторизації, спільні TypeScript-типи між API і UI без кодогенерації, один розробник. Окремий сервіс — це подвоєння операційного навантаження заради гнучкості, яка сьогодні не потрібна.

Дисципліна, щоб винесення лишалось дешевим:
- вся робота з даними — у `lib/server/queries/*.ts`, чисті функції `(params) → data`, без залежності від Next-специфіки (`Request`, `cookies`, тощо);
- route handler = тонкий шар: auth → валідація параметрів (zod) → виклик query → envelope;
- версіонування шляху `/api/v1/...` з першого дня.

Коли реально знадобиться окремий сервіс: (а) payment scoring модель (Python) почне віддавати прогнози в дашборд, (б) white-label клієнти отримають API-доступ. Тоді — окремий Python-сервіс поруч, а не переписування.

### 3.2 Форма відповіді

```jsonc
GET /api/v1/product/overview?from=2025-01&to=2026-07&complex_id=all

{
  "data": [
    { "report_month": "2026-07", "complex_id": "…", "complex_name": "…",
      "total_users": 30148, "confirmed_users": 18692, "confirmed_rate": 0.62, … }
  ],
  "meta": {
    "snapshot_at": "2026-08-05T06:00:00Z",
    "freshness": "fresh",
    "metric_ids": ["PROD-001","PROD-002","PROD-004"],
    "tenant_id": "urbanstack"
  }
}
```

Ендпоінти рівня "секція дашборду", не рівня "таблиця БД" — щоб одна секція = один запит:

```
/api/v1/product/overview          PROD-001..004, 011, 012
/api/v1/product/activation        PROD-008
/api/v1/product/engagement        PROD-009, 010
/api/v1/product/retention         PROD-007, 013
/api/v1/insights?month=&domain=   аномалії + наратив
/api/v1/meta/metrics              реєстр метрик для тултипів
/api/v1/operational/*             пізніше
/api/v1/finance/*                 пізніше
/api/v1/agent/chat                пізніше
```

### 3.3 Реєстр метрик як контракт API

`docs/metrics_registry.md` — уже джерело правди для людей. Пропозиція: завести **машиночитний близнюк** `docs/metrics.yml` (id, `label_ua`, definition, formula, unit, `direction_good`, owner, status, `dbt_model`, `known_issues`), з якого:
- генерується TypeScript `lib/metrics.ts` — типи й лейбли для UI;
- живляться тултипи "що це за метрика" прямо в дашборді (по кліку на заголовок картки — визначення, формула, власник методології, відомі проблеми);
- береться контекст для агента (§7.3);
- CI-перевірка, що кожне поле API має існуючий `metric_id`.

Найчистіше — зробити YAML джерелом, а markdown-таблицю генерувати з нього (парсити markdown-таблиці назад крихко). Це рішення для обговорення, не блокер.

### 3.4 Мультитенантність з першого дня (дешево зараз, дорого потім)

Кожна serving-таблиця несе `tenant_id`, кожен запит API бере tenant з сесії, сьогодні це константа `urbanstack`. Коли підʼїде white-label (`CLAUDE.md` Фаза 4) — не буде міграції схеми й переписування всіх запитів. Вартість зараз: одна колонка й один `WHERE`.

## 4. Авторизація й шеринг (R3, R5)

**Auth.js (NextAuth) + Google OAuth + allowlist.** Микита, Артем, Максим уже мають Google-акаунти — логін в один клік, паролів не заводимо (і не зберігаємо).

```
users(email, name, role, created_at)
role ∈ { admin, product, operations, finance, viewer }
```

- `admin` (Микита) — усе, включно з технічними сторінками (свіжість, логи запусків, dbt-тести).
- `product` (Артем, Максим) — продуктовий дашборд.
- `operations` / `finance` — відповідні дашборди, коли зʼявляться.
- Ім'я й аватар залогіненого — у шапці (Микита просив, щоб "підсвічувалось", хто дивиться).

Що робимо коли:
- **Фаза B (одразу):** логін + allowlist + грубий поділ "адмін / не адмін". ~пів дня роботи, і це рівно те, що потрібно, щоб кинути посилання Максиму.
- **Фаза E (з операційним/фінансовим):** гранулярні ролі, бо там глядачів більше і фінанси не для всіх.

Чого свідомо **не** робимо: власна реєстрація, паролі, скидання паролів, інвайти. Allowlist + Google достатньо для команди з 5–15 людей.

## 5. Фронтенд-стек (R6)

- **Next.js 15 App Router + TypeScript + Tailwind.** Server Components тягнуть дані на сервері → у браузер не їде ні креденшел, ні зайвий JS.
- **shadcn/ui** — базовий шар: layout, картки, таби, таблиці, тултипи, форми, темна тема.
- **Bklit UI** — верхній шар: дашбордні блоки, KPI-картки, анімації/motion, ті патерни, заради яких ти його й хотів.
- **Recharts** (на ньому побудовані shadcn charts) — графіки. Один графічний рушій на весь дашборд, не змішувати.

⚠️ Головний ризик двох бібліотек — два дизайн-системи, що воюють між собою (свої токени кольорів, свої радіуси, свої тіні). Перше завдання Фази B: **звести обидві до одного набору Tailwind-токенів** і зафіксувати правило "хто чим володіє" (shadcn = примітиви, Bklit = композитні блоки). Інакше через місяць буде франкенштейн. Спосіб інсталяції Bklit UI (registry / copy-paste компонентів) — уточнити на старті.

Кешування: `revalidate`-теги, які скидає export job. Сторінка віддається з кешу → 10 глядачів одночасно не створюють жодного навантаження на Postgres (R4).

## 6. Сторітелінг продуктового дашборду (R7)

Не порт Looker. Одна сторінка зі скролом і липкою панеллю фільтрів (період + ЖК), пʼять секцій — це класична воронка **Acquisition → Activation → Engagement → Retention → Action**, розказана мовою UrbanStack.

Правило для кожної секції: спочатку **речення з реальним числом**, потім графіки, які це речення підтверджують. Саме речення робить це історією, а не стіною плиток.

| # | Секція | Питання, на яке відповідає | Метрики |
|---|---|---|---|
| 0 | **Шапка** | "Що зараз?" | 4–5 headline KPI + дельта до попереднього місяця + свіжість даних |
| 1 | **Скільки нас** | Яка база і наскільки вона реальна? | PROD-001 потенційні, PROD-002 підтверджені, PROD-004 % підтверджених, PROD-011 заселеність, PROD-012 типи обʼєктів |

Деталі, які роблять дашборд самодостатнім для глядача, що не в темі:
- клік на заголовок картки → визначення метрики, формула, власник методології, відомі проблеми (з реєстру, §3.3);
- метрики зі статусом `Known issue` в реєстрі (напр. PROD-012) показуються з явним попередженням, а не тихо;
- скрізь дельта до попереднього періоду + напрямок "добре/погано" з `direction_good`.

## 7. Інсайти (R8) — три шари, у порядку надійності

### 7.1 Шар A: детермінований детектор аномалій (dbt, без LLM)

Ядро — **`srv_metric_timeseries` у long-форматі**:

```
tenant_id · metric_id · dimension_key · dimension_value · report_month · value
```

⚠️ Це **єдиний `srv_`-обʼєкт, який будується для всіх доменів** — і саме тому, що він не копія (§1). Це **зміна форми**: усі 38 метрик реєстру, розкидані по десятку wide-таблиць з різними колонками, зводяться до однієї вузької. Виграш не в розмірі, а в тому, що зʼявляється одна сутність замість десятка:

- один рушій аномалій на всі метрики замість окремого детектора під кожен графік;
- анотації на будь-якому графіку читаються з однієї таблиці;
- агент (§7.3) має один обʼєкт для запитів, а не мапу «яка метрика в якому mart'і».

Ціна — цей шар треба поповнювати при додаванні нової метрики. Але це рядок у мапінгу «metric_id → mart.колонка», а не дублікат моделі; і він природно живе поруч із `metrics.yml` (§3.3).

`srv_metric_anomalies` — по кожній парі (метрика × розріз):
- MoM-дельта абсолютна й відносна;
- робастний z-score на ковзному вікні 6–12 місяців (**медіана + MAD**, не середнє+σ — на 12 точках один викид ламає σ);
- поріг: `|z| > 3` або `|MoM %| > поріг метрики`;
- поля: `direction`, `magnitude`, `severity`, `explanation_template` (готовий рядок українською).

**Обовʼязковий запобіжник:** прапорець `is_suspected_data_gap`. Якщо просідання метрики збігається з обвалом кількості рядків у джерелі (той самий липневий кейс з білінгом) — це не інсайт "борг зник", це "дані не доїхали", і показувати це треба інакше. Без цього прапорця перший же авто-інсайт, який побачить СЕО, буде хибним.

UI: маркер на графіку в точці аномалії + підпис під ним. Детерміновано, дешево, однаково для всіх глядачів.

### 7.2 Шар B: LLM-наратив

✅ **Реалізовано** — `web/scripts/build-narrative.mjs` → `web/data/narrative.json`
→ компонент `<Narrative>` на всіх 5 сторінках. Не ендпоінт: за архітектурою
§8в CLAUDE.md ні бази, ні API-сервера немає, тому це крок складання, а
результат комітиться разом з даними й збирається в нічному прогоні окремим
кроком (`continue-on-error`: наратив не має права вбити оновлення даних).

**Модель — OpenAI `gpt-5.6-luna`, `effort: low`, структурований вихід.**
Перемикається `NARRATIVE_MODEL` / `NARRATIVE_EFFORT` без релізу. Вибір
постачальника тут навмисно дешевий: від моделі потрібні 2-3 речення по
ГОТОВИХ фактах, а за правильність чисел відповідає перевірка, а не бренд.
Витрата — ~1,2 тис. вхідних і ~0,2 тис. вихідних токенів на прогін.

⚠️ **Поки функція на обкатці — її видно лише поштам зі списку `LAB_EMAILS`**
(`web/lib/lab.ts`). Це не третя вісь доступу поруч із роллю й областю: ті
описують постійну структуру дашборду й редагуються в адмінці, а це
тимчасовий вимикач, який зніметься одним рядком. Дефолт fail-closed:
порожня змінна = залогіненим не видно нікому. Без сесії видно — інакше
локальний перегляд показував би порожнечу замість функції, яку саме зараз
і роблять.

Чотири речі, які виявились важливішими за сам промпт:

1. **Перевірка чисел після генерації.** Промпт просить не рахувати;
   перевірка це ЗАБЕЗПЕЧУЄ: усі числа з тексту звіряються з рядками
   детектора, і секція, де знайдено чуже число, відкочується на
   детермінований шаблон. Тести (`build-narrative.test.mjs`, 7 шт.) ловлять
   класичну галюцинацію — модель сама віднімає 1 096 − 945 і пише «втрачено
   151 користувача».
2. **Секції без аномалій не йдуть у модель узагалі.** «Нічого незвичного» —
   найчастіший випадок (у серпні 2026 чотири секції з п'яти), і давати
   моделі шанс щось про нього написати немає причини.
3. **Наратив завжди про останній ЗАКРИТИЙ місяць.** Поточний неповний за
   визначенням (`data_drift_findings.md` §B) — інакше першого числа кожного
   місяця дашборд повідомляв би про обвал.
4. **Ключ секції звіряється терпимо.** У payload їдуть і `section`
   ("audience"), і `section_title` ("Аудиторія"), і модель час від часу
   вертає в полі `section` саме заголовок. Зі строгим порівнянням це давало
   через раз ТИХИЙ відкат на шаблон: текст згенеровано, гроші витрачено, а
   на дашборді детермінований рядок і жодного сліду в логах. Тепер ключ
   нормалізується, а секція з фактами, на яку модель нічого не повернула,
   пише в лог, що саме вона прислала.

⚠️ **Підпис показника береться з РЯДУ (`label_ua` в seed'і), а не з картки
реєстру.** Одна картка покриває кілька рядів: PROD-041 — це і потенційні, і
підтверджені, і MAU по ЖК; PROD-011 — і користувачі модуля, і покриття. Поки
підпис брався з реєстру, перший же наратив написав «Житлові комплекси»
тричі поспіль з різними числами. Тепер seed тримає підпис ряду, а `metric_id`
лишається посиланням на визначення й відомі проблеми.

Без `OPENAI_API_KEY` скрипт не падає, а віддає детерміновані шаблони —
`npm run refresh` лишається робочим без ключа.

Оригінальний задум нижче лишається чинним.

Ендпоінт бере рядки аномалій + визначення метрик з реєстру → генерує 2–3 речення на секцію.

- Рахується **один раз після кожного оновлення даних**, результат кладеться в Postgres. Не на кожен перегляд.
- Наслідок, який важливий саме для шерингового дашборду: Микита й Артем бачать **однаковий текст**. Якщо генерувати на льоту, двоє людей отримають різні формулювання про ті самі цифри — і почнеться "а в мене написано інакше".
- Латентність і вартість обмежені й передбачувані.
- **Усі числа — тільки з рядків аномалій**, модель їх не рахує й не вигадує.

### 7.3 Шар C: чат-агент по дашборду

Ендпоінт `/api/v1/agent/chat`, Claude з tool use.

Інструменти — **не вільний SQL**, а вузький білий список параметризованих запитів до serving-store:

```
list_metrics(domain)
get_metric_timeseries(metric_id, dimension?, from, to)
get_anomalies(month, domain?)
compare_complexes(metric_id, month)
get_metric_definition(metric_id)
```

Заземлення: системний промпт містить реєстр метрик — визначення, формули, власників, **відомі проблеми**. Тому агент коректно відповідає і на "як рахується STAR", і на "чому цифра дивна" ("ця метрика має відомий баг з deactivated_houses").

Запобіжники: read-only; кожне число — з результату інструмента, ніколи з голови; у відповіді — `metric_id` і дата зрізу; на питання поза реєстром — чесне "не знаю", а не імпровізація.

**Чому агент останній.** Агент поверх даних, яким ще не довіряють, гірший за його відсутність: він упевнено переказує неправильні цифри, і довіра до всього дашборду падає одразу. Спершу — детермінований шар A, який видно й можна перевірити очима.

## 9. Що вже готове, а що блокує

**Готове й перевикористовується:**
- **Продуктові моделі — готові, 242/242 тести проходять** (виправлено v0.2: у v0.1 тут було «їх ще немає» — їх не було видно з гілки плану, див. блокер 1);
- `dbt_product` / `dbt_operational` mart'и — вже serving-ready за розміром, їдуть у Postgres напряму (§1);
- `int_space_geo` — спільний геоланцюжок для всіх доменів;
- `docs/metrics_registry.md` — готовий контракт для API, тултипів і агента;
- `dbt_finance` — повний ланцюжок, звірений рядок-в-рядок з продакшн-view.

**Блокери / залежності:**
1. **Нічого не закомічено.** Продуктові моделі, `int_user_exclusions`, `fct_users_monthly`, seeds і доки лежать у робочому дереві `master` як untracked/modified. У BigQuery таблиці вже є — звідси й розбіжність v0.1 плану («моделей немає»): з гілки плану їх не видно, бо комміту не існує. Мержити нічого — спершу треба закомітити.
2. **Немає service account для unattended dbt.** Зараз `dbt build` руками під особистим `gcloud auth application-default`. GitHub Actions так запускати не можна — це реальний блокер §2.4, а не деталь.
3. **Каденція Stitch** — не заміряна. Визначає стелю свіжості (§2.3) і годину cron.
4. **Спосіб інсталяції Bklit UI** — уточнити перед Фазою B.

**Хвости, які не блокують Фазу A, але мають бути закриті:**
- джерело останнього графіка Стр.5 продуктового дашборду так і не знайдено;
- ~~**дрейф даних vs PDF**~~ — ✅ **закрито**, `docs/data_drift_findings.md`. Це були два різні явища: (а) ретроактивна мутація історії (атрибути юзера читаються as-of-today і застосовуються до всіх місяців) і (б) дозагрузка подій (3–5% приходять після кінця місяця). «Розрив із PDF» — не втрата даних: числитель у Looker рахувався **без join до бази користувачів**, тобто старий дашборд завищував. Відповідь Артему на «чому не сходиться з Looker» є;
- дірка в білінгу за липень 2026 (`CLAUDE.md` §8а) — до фінансового дашборду, інакше детектор аномалій ловитиме її щомісяця.

**Лишається одне дрібне рішення (дефолт — YAML, якщо не заперечиш):** `docs/metrics.yml` як машинне джерело правди, з якого генерується markdown-таблиця реєстру — щоб два файли не розʼїхались так само, як розʼїхались хардкод-списки будинків (`CLAUDE.md` баг #1).

### Наслідки прийнятих рішень для реалізації

- **Supabase EU** → регіон проєкту обовʼязково `eu-central-1`/`eu-west-*`, щоб не тягнути дані з EU-BigQuery через Атлантику й не ламати резидентність.
- **Vercel** → функції пінимо в EU-регіон (`fra1`); cron лишається в GitHub Actions (не Vercel Cron), бо export job довший за ліміт serverless-функції.
- **Раз на добу** → `revalidate` кешу Next.js прив'язаний до export job, не до таймера. Сторінка перегенерується рівно тоді, коли приїхали нові дані.
- **Логін одразу** → `users(email, name, role)` заводимо в Supabase з першого дня, але `role` поки має лише два значення (`admin` / `viewer`); розширення до `product`/`operations`/`finance` у Фазі E — це додавання значень, не міграція схеми.
