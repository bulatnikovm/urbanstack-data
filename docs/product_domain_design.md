## 2. Знахідки (перевірено на даних 2026-08-04)

### 2.1 «Відвідувачі» рахуються двома різними способами на одній сторінці 🔴

На Стр.1 співіснують:
- `custom_active_users__4738bf74` → `COUNT(DISTINCT amplitude_id)`
- `custom_retention__aa9975c4` (той самий блок, MAU%) → `COUNT(DISTINCT phone_number)`

`amplitude_id` — **не користувач, а установка додатку**. Виміряно (серпень
2025 → серпень 2026): 20 064 `amplitude_id` на 13 919 телефонів.
**4 115 телефонів (29,6%) мають >1 amplitude_id** (перевстановлення / друга
пристрій), **1 070 amplitude_id мають >1 телефон** (спільний пристрій, родина).

Помісячна різниця:

| Місяць | `COUNT(DISTINCT amplitude_id)` | `COUNT(DISTINCT phone)` | Завищення |
|---|---|---|---|
| трав.2026 | 9 738 | 7 779 | **+25,2%** |
| черв.2026 | 9 612 | 7 804 | **+23,2%** |
| лип.2026 | 9 976 | 8 180 | **+22,0%** |

Те саме завищення сидить у `view_monthly_active_residents.visitors_mau` і
`core_active_mau` (обидва на `amplitude_id`) — тобто у скоркартах Стр.1.
**Рішення:** канонічний user key = телефон (див. 3.2), `amplitude_id`
залишається як `device_id` для метрик установок/версій.

Додатково: колонка `EVENTS_407641.user_id` (власний identity Amplitude)
**100% NULL** — identity resolution в Amplitude не налаштований, тому
`user_properties.phone_number` — єдиний реальний ключ користувача.

### 2.2 Синтаксичний баг у «Медіанна к-сть годин до цінної дії» 🔴

`custom_new_users__d303fc10.sql`:

```sql
WHEN event_type IN ('active_receipt_popup_payment_success_view', 'vote_details_active_btn_vote_tap',
  'request_new_desc_btn_success_ok_tap', 'paid_service_description_popup_success_view' 'widget_home_scrn__view' 'widget_home_key_btn__click')
```

Останні три літерали **без ком**. BigQuery конкатенує суміжні рядкові літерали
(перевірено: `SELECT 'a' 'b' 'c'` → `abc`), тому в `IN` потрапляє один
неіснуючий рядок `'paid_service_description_popup_success_viewwidget_home_scrn__viewwidget_home_key_btn__click'`.

Наслідок: три події мовчки не рахуються як «цінна дія» — у т.ч.
`widget_home_key_btn__click` (33 227 подій за 2026) і `widget_home_scrn__view`
(120 668). Метрика **41,2 год** на дашборді порахована по 3 подіях замість 6.

### 2.5 `house_deactivation_dates` у `view_monthly_active_residents` — мертвий код 🟡

CTE зі списком 10 будинків із датами деактивації **існує, LEFT JOIN-иться в
`clean_spaces`, поле `deactivated_date` вибирається — і далі ніде не
використовується**. Жодного `WHERE` по ньому немає. Тобто скоркарти Стр.1
насправді деактивовані будинки **не виключають**, попри вигляд коду.
(Порівняй: CLAUDE.md §1 називає механізм цього view «канонічним» — канонічним
є список, але він тут не застосований.)

Це та сама проблема, що вже вирішена в operational-домені через
`dim_house.is_residential` + point-in-time вікно по `deactivated_at`
(див. `dim9000-operational-domain`). Product має переюзати те саме рішення,
а не копіювати хардкод.

### 2.6 Хороша новина: identity join чистий ✅

`JSON_VALUE(user_properties,'$.phone_number')` = `users.phone` матчиться на
**13 925 з 13 928** унікальних телефонів (99,98%). 1 NULL, 1 `'unknown'`,
2 непов'язані. Тобто зв'язка «подія → користувач CRM → приміщення → будинок →
ЖК» будується надійно і без евристик — це знімає головний ризик домену.

5,6% подій узагалі без телефону (563 396 з 10 081 840 за рік) — це
до-авторизаційний трафік (онбординг, екран входу), його треба свідомо
класифікувати як `anonymous`, а не втрачати.

## 3. Проєкт моделей

Датасет: **`dbt_product`** (окремий, за зразком `dbt_operational` — механізм
уже є в `macros/generate_schema_name.sql`, треба лише додати `+schema:
dbt_product` у `dbt_project.yml`).

### 3.1 Sources

Новий блок `postgresqldim9000_product` (фізично той самий датасет, окремо за
конвенцією):

- `EVENTS_407641` — копія Amplitude. **13,4 млн рядків / 5,95 GB, партиційована
  по `event_time` (DAY), кластеризована по `event_type`.** Партиціювання є —
  incremental буде дешевим.

Переюз без дублювання:
- `transactions` → вже є `stg_finance__transactions` (finance)
- `users`, `space_user`, `statistic_citizen` → вже є `stg_dim9000__*` (operational)
- geo → вже є `int_space_geo` + `dim_house` (`is_residential`, point-in-time)

### 3.2 Staging

**`stg_amplitude__events`** — єдина модель, що торкається сирих подій.

```
materialized: incremental
unique_key: event_uuid            -- колонка uuid
partition_by: {field: event_date, data_type: date, granularity: day}
cluster_by: [event_type]
incremental_strategy: insert_overwrite
```

Інкремент із вікном перезапису (Stitch-sync + Amplitude віддають події із
запізненням): `where event_date >= date_sub(max(event_date), interval 3 day)`.

Колонки:

| Колонка | Джерело | Нотатка |
|---|---|---|
| `event_uuid` | `uuid` | PK |
| `event_time`, `event_date`, `event_month` | `event_time` | |
| `event_type` | | ключ до seed |
| `device_id` | `amplitude_id` | **перейменувати** — щоб більше ніхто не порахував це як юзера (баг 2.1) |
| `session_id` | | `-1` → NULL одразу тут |
| `user_phone_sk` | `to_hex(sha256(json_value(user_properties,'$.phone_number')))` | **хеш, не сирий телефон** |
| `is_authenticated` | phone IS NOT NULL AND NOT LIKE '%unknown%' | |
| `os_type` | `platform` → iOS/Android/Other | |
| `version_name`, `device_model`, `country`, `city` | | |

PII: у `stg_dim9000__users` телефон свідомо не вибирається. Щоб не ламати це
рішення, **сирий телефон не виходить за межі staging** — далі скрізь ходить
`user_phone_sk` (той самий SHA256 рахується і на стороні `users`). Мартам
телефон не потрібен взагалі.

### 3.3 Seed — центральний артефакт домену

**`seeds/product_event_catalog.csv`** — 135 рядків, по одному на `event_type`.
Це для product-домену те саме, чим `dim_order_category.csv` став для
operational: одне джерело правди замість 4 списків core-подій (2.3) і 2
розбіжних CASE по модулях (2.4).

| Колонка | Приклад | Призначення |
|---|---|---|
| `event_type` | `vote_details_active_form__tap` | PK |
| `module_code` | `voting` | стабільний ключ (не українська назва!) |
| `module_order` | `6` | сортування на дашборді |
| `is_technical` | `true` для `session_start/end` | виключити з «Інше» |
| `is_core_event` | `true` | список STAR/MAU (10 подій) |
| `star_category` | `3. Голосування` | категорія Стр.4 |
| `is_activation_event` | `true` | воронка Стр.2 |
| `is_value_action` | `true` | «цінна дія» для time-to-value |
| `notes` | | |

Українські назви модулів — окремий seed `product_module_catalog.csv`
(`module_code`, `module_name_ua`, `drop_off_window_days`), щоб вікно відвалу
(30/90/180 днів, зараз захардкожене в CASE у `custom_retention_4`) теж стало
даними.

Guard-тест: singular test, що падає, якщо в подіях з'явився `event_type`,
якого немає в seed — інакше нові події мовчки провалюватимуться в «Інше»,
як зараз.

### 3.4 Intermediate

- **`int_user_identity`** — міст `user_phone_sk ↔ user_id ↔ complex_id/house_id`.
  Будується з `stg_dim9000__users` + `stg_dim9000__space_user` + `owner_id`
  зі `int_space_geo`. Грануляція: `user_id × complex_id` (юзер може бути в
  кількох ЖК — див. відкрите питання Q3). Тут же прапорці `is_verified`,
  `is_deactivated` (`role = 'ROLE_INACTIVATED_CITIZEN'`), `created_at`.
  **Замінює `all_user_mappings`/`clean_spaces`, які скопійовані в 4+ запитах.**

- **`int_events_enriched`** — `stg_amplitude__events` + seed-каталог +
  `int_user_identity`. Грануляція: подія. Додає `module_code`, `is_core_event`,
  `star_category`, `user_id`, `complex_id`.

- **`int_user_sessions`** — `session_id × user_phone_sk`, тривалість, місяць.
  Уніфікує **три різні визначення сесії**, що зараз розходяться:
  `custom_core_events_5` (без відсіву `session_id=-1`, без верхньої межі),
  `custom_events_usage` (з відсівом, cap 14 400 сек), `custom_events_usage_2`
  (те саме, але per user). Канонічне — з відсівом і cap (потребує
  підтвердження, Q4).

- **`int_user_monthly_activity`** — `user_phone_sk × month`: `is_visitor`,
  `is_core_active`, `n_sessions`, `total_time_sec`, прапорці по модулях,
  `cohort_month`, `months_since_cohort`.

### 6.1 Спільний механізм виключення користувачів

**Контекст (Максим):** коли будинок іде з УК, жителів від квартир **навмисно НЕ
відв'язують** — щоб мати змогу повернути їх. Тому в даних немає жодного
прапорця «цей житель більше не наш»: роль лишається `ROLE_CITIZEN` навіть через
рік (ЖК «Севен»). Отже виключення маємо рахувати ми самі.

Створено **`models/intermediate/shared/int_user_exclusions.sql`** — один артефакт
для ВСІХ дашбордів (рішення Микити: «краще створити щось одне по деактивованих
користувачах і переюзати»). Грануляція `user_id × report_month`.

Чотири причини (`exclusion_reason`): `employee` · `test_complex` ·
`role_deactivated` · `house_deactivated`. Чиста база — `is_active_resident`.

Ключова властивість: виключення **похідне** від `houses.deactivated_at`, тому
**оборотне автоматично**. Повернуть будинок в УК — жителі повернуться в
підрахунки без жодних ручних правок. Ніякого seed'а зі списком людей вести не
треба.

Під нею — **`int_user_space_links`** (user × house, власники ∪ мешканці),
теж спільна.

**Підключено до операційного домену:** `fact_user_space` отримав поля
`is_active_resident` / `exclusion_reason` / `is_house_deactivated`.

⚠️ **Але головні операційні лічильники юзерів цим не фільтруються:**
`mart_monthly_complex_overview` бере їх з `fact_citizen_snapshot` — це
ПРЕД-АГРЕГАТ джерела (`statistic_citizen`: готові числа по ЖК за місяць), а не
підрахунок з `users`. Щоб застосувати виключення, ці метрики треба
переписати з нуля на `int_user_exclusions`. Окреме рішення, не робив.

### 6.6 `fact_user_space` — прибрано дубль логіки прив'язки (2026-08-04)

Це той самий клас проблеми, що й решта знахідок цієї сесії: одна сутність,
описана двічі, з розходженням.

**Рішення:** спільний `int_user_space_links` опущено до атомарної грануляції
`user_id × space_id` (раніше був user × house), і `fact_user_space` став
ТОНКОЮ ВИБІРКОЮ над ним. Власної логіки прив'язки в ньому більше немає.
`int_user_identity` (product) згортає той самий спільний шар до user × house.
