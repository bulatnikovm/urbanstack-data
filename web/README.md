## Як влаштовано

Щодоби о **08:00 за Києвом** — задачу запускає Cloud Scheduler у проєкті
`analytics-454817` ([`ops/setup-refresh-scheduler.sh`](../ops/setup-refresh-scheduler.sh)),
а виконує [`.github/workflows/refresh-dashboard.yml`](../.github/workflows/refresh-dashboard.yml):

```
dbt build               під сервіс-акаунтом dbt-runner
  → npm run export-data    BigQuery → data/*.json (13 mart'ів, ~1.2 MB)
                           + data/operational/*.json (16 файлів, ~2.7 MB)
  → npm run build-metrics  metrics.yml + metrics_operational.yml → data/metrics.json
  → git commit + push      Vercel бачить пуш і перезбирає
```

Vercel дивиться **в цей самий репозиторій**, Root Directory = `web`. Раніше
`web/` виносився `git subtree split` у другий репозиторій — це вимагало
другого токена з правом запису в чужий репо і регулярно падало з 403.
Тепер деплой — це просто коміт.

Postgres тут досі немає, і це свідомо: усіх даних 1.2 MB, вони їдуть
закоміченим JSON. Витрина в базі знадобиться, коли підʼїдуть фінанси
(там гігабайти) і коли даних захочуть операційний дашборд та агент —
див. план, §1 і §8.

**Чому розклад не в GitHub Actions.** `schedule` там — не гарантія, а
спроба: під навантаженням запуски відкладаються або МОВЧКИ скасовуються.
Виміряно на цьому репозиторії: «06:00 UTC» стабільно спізнювалось на 40-58
хвилин, 27.08.2026 стартувало о 17:23, а 28 і 29 серпня не стартувало
взагалі — і жодної червоної позначки в Actions, бо падати нічому: запуску не
було. Перенос хвилини з :00 на :17 не допоміг. `workflow_dispatch` при цьому
спрацьовує миттєво (28.08: створено 12:47:55, закомічено 12:55).

Тому розклад живе в Cloud Scheduler (він і так уже крутить пʼять задач у
цьому проєкті), а GitHub лишився виконавцем: задача робить POST на
`actions/workflows/refresh-dashboard.yml/dispatches`. Час — 08:00 за Києвом,
щоб о 09:00 дані вже були на екрані: повний цикл із пересборкою Vercel
укладається в чверть години. Пояс заданий іменем, тож узимку задача
переходить на UTC+2 сама.

Два `schedule` в самому воркфлоу (06:17 і 12:17 UTC) лишились як
безкоштовна підстраховка, якщо відвалиться вже Cloud Scheduler — напр.
скінчиться токен. Подвійної роботи вони не роблять: job `guard` дивиться на
дату останнього коміту в `web/data/` і пропускає прогін, якщо сьогодні дані
вже оновились.

Скрипт є у двох варіантах — `ops/setup-refresh-scheduler.sh` (bash, токен
змінною оточення) і `ops/setup-refresh-scheduler.ps1` (PowerShell, питає
токен прихованим вводом). Другий зʼявився не для симетрії: у PowerShell
немає синтаксису `VAR=значення команда`, тож bash-приклад там розсипається
ще на розборі рядка. ⚠️ `.ps1` має бути збережений у UTF-8 **з BOM** —
PowerShell 5.1 без нього читає файл як ANSI, кирилиця перетворюється на
сміття, і парсер падає.

**Токен.** Задача ходить у GitHub із fine-grained PAT (тільки цей
репозиторій, тільки `Actions: read and write`), який лежить у заголовку
задачі Cloud Scheduler. У токена є термін дії; коли він скінчиться,
оновлення просто перестане приходити — і смуга «Дані не оновились сьогодні»
скаже про це наступного ж дня. Перевипустити й прогнати скрипт ще раз:
`GH_DISPATCH_TOKEN=github_pat_… ops/setup-refresh-scheduler.sh`.

**Як видно, що оновлення не пройшло.** Бейдж у шапці показує час зрізу, а
над сторінкою зʼявляється смуга «Дані не оновились сьогодні» — але тільки
коли справді є проблема; у нормальний день її немає взагалі.

Стан рахується по київських ДОБАХ (`lib/freshness.ts`), а не по годинах від
зрізу. Так було раніше — «до 36 годин зелена крапка», — і 28.08.2026 це
провалилось рівно там, де мало спрацювати: прогін не стартував, на екрані
був учорашній зріз, а минуло 19 годин, тож індикатор лишався зеленим.
Дірка в добу коротша за поріг у півтори. Тепер питання ставиться так само,
як працює конвеєр: зріз сьогоднішній чи ні. До 10:00 за Києвом учорашній
зріз ще вважається нормою (запас на повільний прогін), після — це «не
оновилось». Поріг виведений з обіцянки «о 09:00 дані на місці» плюс година
зверху, тож він переїжджає разом із розкладом.

Свіжість береться зі СТАРІШОГО з двох `_meta.json` (продуктового й
операційного): обидва пише один прогін, але якщо колись відвалиться
половина конвеєра, чесніше показати гіршу цифру.

**Побічний ефект, який варто знати:** оновлення даних = коміт = пересборка.
Тому в історії буде по коміту на добу. Плюс — дані версіоновані: видно, що
саме дашборд показував будь-якого дня, і можна відкотитись.

**Сторінка повністю статична** (`○ Static` у виводі білда). Наслідок: скільки б
людей її не відкрило одночасно, навантаження на щось живе — нуль.

## Команди

```bash
npm run dev            # локально
npm run export-data    # перезалити data/*.json з BigQuery
npm run refresh        # export + build
npm run verify         # ⚠️ ПЕРЕД пушем: реєстр метрик + збірка
```

**`npm run verify` — не формальність.** `next build` НЕ перевіряє покриття
реєстру метрик: це окремий скрипт, і запускає його `build-metrics`. Двічі
поспіль (01.09 і 02.09) нічне оновлення падало саме тому, що локально
ганявся лише `next build`: перший раз через розсинхрон package-lock (його
ловить `npm ci` у чистій комнаті), другий — через картку без запису в
реєстрі. Обидва рази помилка проявлялась не в мене на екрані, а наступного
ранку в конвеєрі.

Автентифікація експорту — та сама ADC, що й у dbt (`gcloud auth application-default login`).

## Період і фільтр дат

Діапазон живе в **URL** (`?from=2024-01&to=2026-08`), не в стані компонента:
посилання на конкретний період можна переслати, і воно відкриється тим самим.
Резолвиться один раз у `getPeriod()` — межі даних відомі лише там.

**Пікер помісячний, не поденний.** Усі марти мають грануляцію `report_month`;
поденний календар обіцяв би точність, якої в даних немає.

Ціна: сторінки стали динамічними (`ƒ` замість `○`) — `searchParams` це
вимагає. Рендер іде з локального JSON, тому це мілісекунди й жодного
зовнішнього виклику; властивість «глядачі не навантажують BigQuery»
збережена.

## Довідка по метриці — і чому вона перевіряється на збірці

Іконка «i» біля заголовка картки бере текст з `docs/metrics.yml` **за
підписом картки**. Якщо запису немає — іконка просто не зʼявляється. Мовчки:
ні помилки, ні попередження.

Так накопичилось **21 картка з 52 без довідки**: підписи міняли, нові блоки
додавали, реєстр лишався позаду. Тому `npm run build-metrics` тепер запускає
`check-metric-coverage.mjs`, і збірка падає, якщо картка не знайшла своєї
метрики. Виняток — два службові блоки в `NOT_METRICS` (порожній стан і
адмінка); усе, що показує цифру про продукт, туди потрапляти не має.

Панель із кількома рядами вказує всі свої метрики:
`metric={["Потенційні користувачі", "Підтверджені", "Відвідувачі додатку"]}` —
довідка покаже три блоки поспіль. Одна довідка на графік із трьома рядами
гірша за її відсутність: виглядає як повне пояснення, а описує третину.

## Живі курсори (приколюха, вимикається)

Хто зараз у дашборді й де його миша. Видно ТІЛЬКИ тим, хто перелічений у
`LIVE_WATCHERS` — решта не бачить ні аватарок, ні курсорів. Транспорт —
Supabase Realtime (він уже є в проєкті під список доступів), канал на
сторінку. Код: `lib/live.ts` + `components/live-presence.tsx`, монтується в
layout дашборду.

Панель у правому нижньому куті: аватарки присутніх на цій сторінці й
тумблер, який ховає чужі курсори, коли вони заважають читати таблиці. Стан
тумблера в localStorage і синхронізується між вкладками.

- **Ніхто не шле координати, поки в каналі немає спостерігача.** Presence
  каже кожному клієнту, чи є кому дивитись; немає — потоку немає взагалі.
  Це і тримає нас у безкоштовному ліміті Supabase (2 млн повідомлень на
  місяць: пʼятеро людей по 10 повідомлень на секунду зʼїли б його за
  тиждень), і означає, що чужі позиції залишають чужий браузер лише поки
  на них справді дивляться.
- **Координати рахуються від `<main>`, не від вікна** — інакше на іншій
  ширині екрана стрілка показувала б помітно не туди.
- **Хто спостерігач, вирішує СЕРВЕР** (layout читає сесію): у клієнтський
  бандл їде готове `canWatch`. Клієнтська перевірка перемикається в
  DevTools за секунду.
- ⚠️ **Це обмеження інтерфейсу, а не захист.** Anon-ключ лежить у бандлі,
  тож підключитись до каналу технічно може будь-хто, кому не лінь. Зробити
  інакше можна тільки видаючи користувачам справжні JWT Supabase, а
  автентифікація в нас через Auth.js/Google, тобто для Supabase усі —
  анонімні.
- Без `NEXT_PUBLIC_SUPABASE_*` і `LIVE_WATCHERS` фіча просто не існує:
  компонент нічого не малює й нікуди не підключається.

## Рішення, які легко зламати назад

- **Частку не рахуємо на базі < 100** (`MIN_RATE_BASE` у `/health`). У 2024
  застосунком користувались одиниці, і тиждень, де біометрію бачила ОДНА
  людина, а поп-ап не показався, давав чесні 100%. Такі точки треба
  **викидати, а не малювати нулем**: `?? 0` опускав лінію в підлогу там, де
  частки просто немає, і це читалось як «збоїв не було».
- **Тижневі картки рахують останній ПОВНИЙ тиждень.** Для місяців ми свідомо
  показуємо незавершений період із позначкою, але у вівторок тижнева метрика
  має один день даних і дельта до повного тижня дає −97% — падіння, якого
  немає. Поточний тиждень лишається на графіках, у шапці сторінки про це є
  рядок.
- **Версії застосунку — топ-5 конкретних збірок, не «актуальна / стара».**
  Поділ на дві категорії не відповідав на питання «на чому люди сидять», а зі
  зміною актуальної версії переписував історію заднім числом. ⚠️ Хто оновився
  всередині місяця, потрапляє у дві версії — сума по версіях більша за
  кількість людей (PROD-033, `known_issue`).
- **Сегменти «Живі / Сонні / Неактивні» — лінії, не стовпчики.** 32 місяці ×
  3 серії = 96 стовпчиків по 2 пікселі на пів-екрана; тренд, який тут і є
  змістом, у такому гребінці не читається.
- **Показуємо ПОТОЧНИЙ місяць, включно з незавершеним** (рішення Микити
  2026-08-05 — потрібен стан «як зараз»). Наслідок: 5 серпня всі місячні
  лічильники в ~6 разів менші за липневі й дельти в мінусі. Тому в шапці є
  позначка «місяць триває · 5 з 31 днів» — прибирати її не можна, інакше це
  читається як обвал.
- **Воронка активації має ДВІ категорії, не три.** У марті
  `count_activated + count_passively_activated == count_new_users` тотожно
  (залишок = 0 у кожному місяці) — «Без активності» була категорією, якої не
  існує.
- **Розподіл по ОС — з `agg_os_monthly`, не з `mart_version_adoption`.**
  В останнього грануляція міс × ОС × ВЕРСІЯ; сума `active_users` по версіях
  рахує двічі того, хто за місяць був на двох версіях (iOS 6 080 замість
  5 153, +18%).
- **`LabelList` з Recharts 3 не рендериться** — перевірено двічі, у чистому
  бандлі теж. Підписи значень робимо або HTML-ом (`ranked-bars.tsx`), або
  окремим графіком.
- **Bklit `<PieCenter>` ламає гідратацію.** `ChartStatFlow` вирішує
  статичний текст чи `<NumberFlow>` через
  `useState(() => customElements.get("number-flow-react"))`: на сервері
  `customElements` немає → `false` → текст; у браузері на першому рендері
  custom element уже зареєстрований на імпорті модуля → `true` → інше
  дерево. React кидає "Hydration failed" (підтверджено в консолі — числа
  прямо в тексті помилки не збігались). Тому `bklit-donut.tsx` має власний
  `PieCenter` — ту саму назву функції `PieChart` розпізнає по
  `isPieCenter()` (перевіряє `.displayName`/`.name`, не референс), тож
  підміна підхоплюється в той самий grid-слот без жодних змін у bklit-коді.
- **Bklit `<PieChart>` без `size` не рендериться в наших макетах.**
  `PieChartInner` має захист `if (size < 10) return null`; без `size` він
  міряє контейнер через visx `ParentSize`, а всередині flex-колонки з
  `items-center` (пончик + легенда під ним) контейнер ніколи не отримує
  визначеної ширини — міряється в 0 назавжди. Задаємо `size` пікселями
  напряму. `innerRadius`/`hoverOffset` там теж пікселі, не частка 0–1 (на
  відміну від shadcn-версії) — легко переплутати вдруге.
- **Вікно від першого місяця бази.** У `mart_activation_monthly` є когорти
  `2010-01` і `2022-06` (по 1 користувачу — зіпсований `created_at` у джерелі).
  Без обрізання вісь розтягується на 16 років.
- **Службовий рядок `report_month_key = "ALL"`** у `mart_time_to_value` — це
  підсумок за весь час, не місяць. У часовий ряд не потрапляє.
- **Максимум 3 категоріальні серії**, кольори не циклимо. STAR має 7 категорій —
  тому це рейтинг, а не 7 ліній на одному графіку.
- **Жодних двох осей Y.**
- Палітра — валідовані слоти з dataviz-довідника (`globals.css`, worst CVD ΔE 9.2).
- `RankedBars` навмисно не на Recharts: `LabelList` не доїжджає в браузерний
  бандл Recharts 3, та й HTML для списку «підпис — смуга — значення» кращий.
- **Шрифт підключається через `--font-sans` / `--font-mono`, не через
  `--font-geist-*`.** `globals.css` містить `@theme inline { --font-sans:
  var(--font-sans) }` — Tailwind бере токен з CSS-змінної з тим самим іменем.
  Скафолдне `--font-geist-sans` її не визначає, `font-sans` не резолвиться, і
  вся сторінка падає на серифний дефолт браузера. Це виглядало як «дашборд у
  Word». Не перейменовувати назад.
- Ця версія shadcn — на Base UI: композиція через `render={<Link/>}`, а не
  `asChild`. З `asChild` проп протікає в DOM і React лається в консоль.

## Три правки в `components/ui/chart.tsx`

Файл shadcn, але змінений локально (це нормально — shadcn копіює код у проєкт).
Обидві правки зникнуть при `shadcn add chart --overwrite`, тому вони тут:

1. **`valueFormatter`** на `ChartTooltipContent`. Штатний `formatter` підміняє
   рядок тултипа **цілком** — разом із маркером і назвою серії, тож тултип
   перетворюється на стовпчик чисел без підписів. `valueFormatter` форматує
   лише число, лишаючи «● Потенційні · 25 020».
2. **`debounce` (120 мс)** на `ResponsiveContainer`. Сайдбар анімує ширину
   200 мс; без дебаунсу кожен графік переміряється й перемальовується на
   кожному кадрі анімації — згортання сайдбара помітно гальмувало.
3. **`gap-6`** у рядку тултипа. `justify-between` сам по собі проміжку не
   гарантує: довга назва серії стикалась із числом впритул
   («Підтверджені12 939»).

Заголовок тултипа форматує `monthTooltip()` («Черв. 2026»), а не `monthShort()` —
останній лишається для підписів осі, де потрібно коротко.

## Авторизація (Auth.js v5 + Supabase)

Два провайдери — корпоративний Microsoft Entra ID і Google, список доступів
— у Supabase (таблиця `dashboard_users`), не в env. Раніше список жив у `ALLOWED_EMAILS`/`ADMIN_EMAILS`, і додати колегу
означало полізти в Vercel і дочекатись редеплою; тепер це робиться зі
сторінки `/admin` в рантаймі, без коміту. Захист трирівневий:

- `proxy.ts` (Next 16; був `middleware.ts` — конвенцію перейменували)
  редіректить неавторизованих на `/login` ДО рендеру сторінки;
- `app/(dashboard)/layout.tsx` — усі сторінки дашборду в route group, окремо
  від `/login`, щоб неавторизований глядач не бачив сайдбар на екрані входу;
- `lib/access.ts` — сам allowlist: `accessFor(email)` ходить у Supabase
  PostgREST звичайним `fetch` (без `@supabase/supabase-js`, щоб зайва
  бібліотека не тягнулась у `proxy`), `fail closed` — недоступна база теж
  трактується як відмова.

**Роль перечитується з бази на КОЖНОМУ запиті** (`auth.config.ts`, callback
`jwt`), а не лише при вході — інакше відкликаний у `/admin` доступ ще
хвилини/години працював би зі старим токеном. Ціна — один запит до Supabase
на запит сторінки; на команді з 5-15 людей це непомітно.

**Ролі — `admin`/`viewer`.** Адмін бачить пункт «Доступи» і може додавати/
прибирати людей та міняти ролі; останнього адміна прибрати не можна
(`removeUser` в `lib/access.ts` це блокує). Гранулярніші ролі
(product/operations/finance) — Фаза E.

### Корпоративний вхід (Microsoft Entra ID)

Навіщо: gmail-доступ живе окремо від кадрових процесів — людина йде, її
пошта лишається робочою, і закривати треба руками в `/admin`. З M365
достатньо вимкнути обліковий запис, і вхід відвалюється сам. Плюс single
tenant не пускає до екрана входу нікого, крім `@dim9000.com`.

**Підключення умовне.** Немає всіх трьох змінних — немає ні провайдера, ні
кнопки на `/login`; Google працює як працював. Це не косметика, а страховка
міграції: обидва провайдери мусять бути живі одночасно, поки всі не
отримають рядок з робочою поштою в `/admin` і не перелогіняться. Замінити
Google на Microsoft одним кроком = закрити всіх, включно з єдиним адміном,
і повертати доступ SQL-ом у Supabase.

Що робить сисадмін в Entra ID (App Registration):

- single tenant, платформа **Web**;
- redirect URI `/api/auth/callback/microsoft-entra-id` — на проді й на
  `http://localhost:3000`;
- client secret на 24 місяці (**зафіксувати дату** — прострочення виглядає
  як «вхід зламався», без жодної помилки в коді);
- **Token configuration → optional claim `email`** для ID-токена;
- дозволів понад `User.Read` не треба.

⚠️ **`AUTH_MICROSOFT_ENTRA_ID_ISSUER` — з tenant ID.** Без нього провайдер
підставляє `/common/`, тобто «будь-який обліковий запис Microsoft у світі».
Список доступів чужого все одно не пустить, але відмовляти має вже екран
входу Microsoft.

⚠️ **Закінчується на `/v2.0`, без слеша в кінці.** Auth.js звіряє цей рядок
з полем `issuer` well-known-документа символ у символ
(`processDiscoveryResponse` в `oauth4webapi`), а Microsoft віддає його без
слеша — зі слешем вхід падає ще на discovery, до будь-якого редіректу.

⚠️ **Пошта в токені — це optional claim, а не даність.** Якщо його не
ввімкнули, `user.email` порожній, `signIn` повертає `false`, і людина, яка в
списку доступів Є, отримує «немає доступу» без натяку, чому. Тому в
`auth.config.ts` профіль провайдера обгорнутий: пусту пошту підміняє
`preferred_username` (для робочих акаунтів це UPN, та сама
`name@dim9000.com`). Дірки в безпеці тут немає — що б не приїхало, воно
звіряється зі списком у Supabase.

Порядок міграції: дві кнопки → корпоративні адреси в `/admin` → усі
перелогінились → прибрати Google (провайдер і змінні) → оновити
`LIVE_WATCHERS`, бо там пошта, і при зміні адреси фіча мовчки зникає.

### Як увімкнути (нічого не працює без цього)

1. [Google Cloud Console](https://console.cloud.google.com/apis/credentials) →
   **APIs & Services → Credentials → Create Credentials → OAuth client ID**,
   тип **Web application**.
2. Authorized redirect URIs:
   - `http://localhost:3000/api/auth/callback/google` (локально)
   - `https://<домен-на-vercel>/api/auth/callback/google` (прод, додати
     пізніше, коли буде відомий домен)
3. Supabase-проєкт (URL і `service_role` ключ — Project Settings → API).
   Таблиця `dashboard_users`: `email` (унікальний індекс по `lower(email)`),
   `role` (`admin`/`viewer`), `note`, `created_at`, `created_by`. RLS закрита
   наглухо — читається лише через `service_role` з сервера.
4. Скопіювати `.env.local.example` → `.env.local`, заповнити:
   - `AUTH_SECRET` — `npx auth secret` або `openssl rand -base64 33`
   - `AUTH_GOOGLE_ID` / `AUTH_GOOGLE_SECRET` — з кроку 1
   - `SUPABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY` — з кроку 3
   - `AUTH_MICROSOFT_ENTRA_ID_ID` / `_SECRET` / `_ISSUER` — від сисадміна
     (див. «Корпоративний вхід» вище). Без них просто немає другої кнопки.
5. Собі — перший рядок у `dashboard_users` руками (SQL editor у Supabase,
   `role = 'admin'`): без жодного рядка в таблиці зайти нікому, а `/admin`
   доступний лише вже впущеному адміну — курка-яйце розв'язується один раз
   вручну.
6. На Vercel ті самі змінні через **Project Settings → Environment
   Variables** — `AUTH_SECRET` там окремий, не той, що локально.

⚠️ `SUPABASE_SERVICE_ROLE_KEY` обходить RLS — у браузер не потрапляє ніколи
(файл `server-only`), на Vercel додавати як звичайну (не Public) змінну.

Без `.env.local` логін впаде на `Configuration` error — це очікувано, ще не
підключені креди, а не баг коду. Уся решта (типи, збірка, `proxy.ts`)
перевірена без живого OAuth-обміну.

## Що спільне в двох дашбордів — і чому

Два домени злиті в один застосунок 2026-08-25. Спільне тут не з економії, а
тому що інакше воно розходиться:

| Спільне | Чому |
|---|---|
| логін і список доступів | одна людина — один вхід; два allowlist це два джерела правди. `/admin` лишився один, продуктовий |
| компоненти (`components/`, 123 файли) | у двох теках вони вже почали розходитись: `page-header.tsx` і `bklit-line.tsx` в операційному пішли вперед, і правити довелося б двічі |
| реєстр метрик на виході (`data/metrics.json`) | картки обох дашбордів шукають довідку тим самим `getMetric(label)` зі спільного `dashboard.tsx` |
| воркфлоу оновлення | один `dbt build` на обидва домени, один коміт |

Роздільним лишилось те, що справді роздільне:

- **джерела реєстру** — `docs/metrics.yml` і `docs/metrics_operational.yml`
  ведуться окремо (різні власники методології, різний темп). Підпис метрики
  при цьому має бути унікальним НАСКРІЗНО: `build-metrics` падає на дублікаті,
  бо саме по підпису шукає UI. Коли той самий показник потрібен в обох
  доменах — картка вказує запис явно (`metric="Підтверджені (ЖК)"` при підписі
  «Підтверджені» на екрані);
- **шар даних** — `lib/data.ts` і `lib/data-operational.ts`, свої типи й своя
  тека вивантажень. Спільних мартів у доменів немає, зливати нічого;
- **вивантаження** — окремі скрипти, тож падіння одного лишає другий домен
  тим, що був.
